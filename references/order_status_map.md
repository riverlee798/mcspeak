# order_status_map.md — 订单状态映射 + 麦当劳 App 界面词汇对照

> **两份独立证据，别混用**：
> 1. `mcd-mcp` 的 `query-order` 返回的 `orderStatus`（中文文字）+ `status`（数字字符串）；
> 2. 访客在**麦当劳 App 订单页**上真实看到的文字。
>
> 数据来源：2026-10-24 对门店 `3350020` 的真实下单实测（`samples/17`–`21`），
> 以及**一次真实付款并成功取餐**（阿拉伯语用户，经典麦旋风）的 App 实况记录。
> **工具文档里的 `status` 枚举与实测不符，一律以本表为准。**

## 1. 订单状态总表（按真实出现顺序）

| # | 状态文字 | `status` 码 | 含义 | 用户该做什么 | 证据强度 |
|---|---|---|---|---|---|
| 1 | **待支付** | `10` | 订单已创建，**还没付钱**，有付款时限（实测 15 分钟） | 立刻付款；不想买了就点「取消订单」 | ✅ **接口实测**（`samples/17`、`18`）+ App 一致 |
| 2 | **确认中** | 待校正 | 钱已付，系统/门店正在确认这一单（通常几秒到一分钟） | 什么都别做，等它跳下一步。**别重复下单** | ✅ **App 实测**（真实付款）；接口码未取到 |
| 3 | **配餐中** | 待校正 | 门店已接单，后厨在做 | 在取餐台附近等，留意叫号屏 | ✅ **App 实测**；接口码未取到 |
| 4 | **待取餐** | 待校正 | **餐已做好，等你去拿** ★ 这是取餐的主信号 | **现在就去取餐台，出示取餐卡** | ✅ **App 实测**；接口码未取到 |
| 5 | **订单已准备完毕** | 待校正 | 备餐流程走完、餐点已就位（取餐的最后确认态） | 拿餐、当场核对有没有少东西 | ✅ **App 实测**；接口码未取到 |
| 6 | **订单已完成** | `40` | 订单结束（已取餐 / 已超时结案） | 不需要操作 | ✅ **接口实测**（`samples/20`） |
| 7 | **订单已取消** | `60` | 超时未付，系统**自动关闭**（App 上没有"已过期"这个词） | 重新下单；**不会扣款** | ✅ **接口实测**（`samples/19`） |
| 8 | 订单已取消（用户主动） | 待校正 | 访客自己点了「取消订单」 | 退款原路退回；需重新下单 | ⏳ 待校正（是否同为 `60` 未知） |
| 9 | 已评价 / 退款中 / 已退款 | 待校正 | 取餐后的评价与退款流程 | 等 1–7 个工作日 | ⏳ 未测 |

> **★ 取餐的关键判据**：`待取餐` 或 `订单已准备完毕` → 可以去拿。
> 代码里用**两个文字都命中**就放行，同时用 **`pickupCode` 非空**做兜底，不要只依赖某个魔法数字。

> **码值体系**：实测 `10 / 40 / 60`，工具文档写的是 `1/2/4/6/7/8/10`，**两套完全不合**。
> 文档那套很可能是另一条业务线或旧版。mcspeak **一律按文字匹配**，码只做辅助；未测到的码当 `unknown`。

## 2. ⚠️ App 上「取餐码」显示为「订单号」

**这是最容易让访客误解的一处**：

- 接口字段叫 `pickupCode`（我们内部叫「取餐码」）；
- 但**麦当劳 App 订单页上，这个号码的标签写的是「订单号」**；
- 而接口里另有一个 `orderId`（我们是**不展示**的）。

所以卡片上必须写清楚：

> 卡片上的「取餐码 12345」= App 里那一行「**订单号 12345**」。
> 不是让你报给客服的长串编码，是**柜台叫号用的那个短号**。

**同时**：`pickupCode` 付款前是空串 `""`，付款成功后才产生（实测 5 位纯数字字符串，当字符串处理，别转 int 丢前导 0）。

## 3. 麦当劳 App 界面词汇对照表

> 用途：外国游客看不懂 App 上的中文。**取餐卡要放这张表的精简版**，让他能对着自己的手机屏幕找到按钮。

| 中文原文 | English | 含义 | 用户看到它该做什么 |
|---|---|---|---|
| 待支付 | Awaiting payment | 订单还没付款 | 赶紧付款，超时会自动取消 |
| 确认中 | Confirming | 已付款，正在确认订单 | 等几秒，别重复下单 |
| 配餐中 | Preparing | 后厨在做你的餐 | 在取餐台附近等 |
| 待取餐 | Ready for pickup | **餐好了，可以去拿** | 现在就去取餐台 |
| 订单已准备完毕 | Order ready | 备餐完成，餐点已就位 | 拿餐并当场核对 |
| 订单已完成 | Completed | 整单结束 | 不需要操作 |
| 订单已取消 | Cancelled | 订单已关闭（多为超时未付） | 未扣款，可重新下单 |
| 去支付 | Pay now | 付款按钮（**黄色实心胶囊**） | 点它 → 扫码或调起支付 |
| 取消订单 | Cancel order | 取消按钮（白底黑边，**最左边**） | 不想买了点这里，未支付取消不扣钱 |
| 联系客服 | Contact support | 客服入口（白底黑边，**中间**） | 有异常（扣钱没出餐）点这里 |
| 就餐方式 | Dining method | 堂食还是带走 | 核对是「堂食」还是「外带」 |
| 堂食 | Dine-in | 在店里吃 | 找座位，别拿打包袋 |
| 外带 | Takeaway | 点了带走 | 拿到餐就可以走 |
| 预计取餐 | Estimated pickup | 预计什么时候能拿到 | 在这个时间前后去柜台 |
| 餐具需求 | Cutlery | 要不要餐具 | 「不需要餐具」= 没给叉勺，需要就找店员要 |
| **订单号** | **Order number（实为取餐号）** | **柜台叫号用的短号，就是我们的「取餐码」** | **最重要：凭它取餐** |
| 订单编码 | Order reference | 长串编码，申诉/查询用 | 出问题时报给店员或客服，**不要拿去取餐** |
| 实付 | Amount paid | 实际付了多少钱 | 核对金额 |
| 商品小计 | Subtotal | 商品金额 | 核对价格 |
| 合计 | Total | 应付总额 | 核对要付多少 |
| 我已取餐 | I've collected it | 确认已拿到餐的按钮 | 拿到餐后点一下 |
| 再来一单 | Order again | 用同样的内容再下一单 | 想再吃一次时点它 |
| 开发票 | Invoice | 开电子发票 | 需要报销时点它 |

### 各状态的英文对照（卡面用）

| 中文 | English | 该做什么（英文） |
|---|---|---|
| 待支付 | Awaiting payment | Pay before {time} or the order is cancelled |
| 确认中 | Confirming | Give it a few seconds — don't order twice |

## 4. 取餐卡精简版（直接印在卡片背面）

> 只放 **7 行**，多了没人看。中文给店员、用户语言给访客。

```
┌──────────────────────────────────────────┐
│  🎫 取餐码  PICKUP CODE                   │
│        0 0 0 0 0                         │  ← 字号最大
│  App 里这一行叫「订单号」                  │
│                                          │
│  待支付    → 先付款                       │
│  确认中    → 等几秒                       │
│  配餐中    → 在取餐台附近等                │
│  待取餐    → 现在去拿 ★                   │
│  已完成    → 不用操作                     │
│                                          │
│  给店员：您好！我在手机上点好了，           │
│          取餐码是 00000，谢谢！            │
└──────────────────────────────────────────┘
```

**规则**
- **`pickupCode` 为空时不要印这张卡**（付款前是 `""`），改印「柜台卡」或「待付款卡」。
- 状态行**只高亮当前那一条**，其余灰掉。
- 卡片上的价格标签写「**实付**」（不是「参考价格」）—— 取餐时已经付过钱了。
- 「订单编码」不要出现在卡面上，只作申诉用。

## 5. 本地化注意

`orderStatus` 是**中文文字**（如 `待取餐`），`status` 是**数字字符串**（如 `"10"`）。

```js
// 正确：先按文字匹配（稳定），再按码兜底
const STATUS = {
  '待支付':         { code: '10',   key: 'status.unpaid',    action: 'pay' },
  '确认中':         { code: null,   key: 'status.confirming', action: 'wait' },
  '配餐中':         { code: null,   key: 'status.preparing',  action: 'wait' },
  '待取餐':         { code: null,   key: 'status.ready',      action: 'collect' }, // ★
  '订单已准备完毕': { code: null,   key: 'status.ready',      action: 'collect' }, // ★
  '订单已完成':     { code: '40',   key: 'status.completed',  action: 'none' },
  '订单已取消':     { code: '60',   key: 'status.cancelled',  action: 'reorder' },
  // 未收录的一律落到 unknown：显示原文字 + 通用建议，不猜
};
```

**禁止**：不要用 `status === '10'` 硬编码判断"待支付"之外的含义；码值文档不可信（文档说 10 = 配餐中，实测 10 = 待支付）。

**RTL 语言**（阿拉伯语等）在对话里输出状态时，给状态文字加 RLM / RLI 隔离，避免后面的括号、编号跑位（见 `SKILL.md` 核心原则 10）。
