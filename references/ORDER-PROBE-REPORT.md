## 1. `create-order` 字段结构

```

├─ orderId            "1030000000000000000000000001"   订单号
├─ payId              "1030000000000000000000000001"          支付单号
├─ payH5Url           "https://m.mcd.cn/mcp/scanToPay?orderId=..."   ★ 唯一来源
└─ orderDetail                              ★ 多一层包裹

   │  ├─ price        "33.5"                            元字符串

   ├─ totalAmount "33.5" / realTotalAmount "33.5" / totalDiscountAmount "0"
   ├─ couponList[]{ couponName, discountAmount }         空数组时无券

   ├─ pickupCode      ""                                ★ 未付款为空
```

**没出现的字段**（到店自取场景）：`deliveryInfo`、`lockerCode`、`lockerQrCode`、`tablewarePrice`、`realPackingFeeTotalPrice`、`mealAssistance`。→ **全部按可选处理**。

## 2. `query-order` 字段结构

**与 `orderDetail` 几乎同构，但：**

| 差异 | create-order | query-order |
|---|---|---|
| 外层包裹 | `data.orderDetail` | `data`（平铺） |
| `payH5Url` | ✅ | ❌ **没有** |
| `payId` | ✅ | ✅ |
| 结构 | 有一层嵌套 | 平铺 |

```js
// 必须的归一化
const o = raw.data.orderDetail ?? raw.data;
```

`comboItemList` 在 `query-order` 里多了字段说明：`itemName` = "子项或特调定制信息"，`itemQuantity` = 数量。

## 3. `order-list` 字段结构（顺带补测）

```
data.list[]
├─ orderId / orderType "1" / beType "1" / beCode "" / storeCode / storeName
├─ createTime
├─ orderStatus        "订单已完成" / "订单已取消"     ★ 只有文字，没有 status 码
├─ orderProductList[]{ productCode, productName, quantity,
│                      comboItemList[]{ productCode, name, quantity } }   ★ 结构化！
└─ realTotalAmount
```

**关键差异**：`order-list` 的 `comboItemList` 是**结构化的**（有 `productCode` + `name`），而 `query-order` 是**拼好的中文串** `itemName`。
→ 做"历史订单再点一单"要用 `order-list`；做"定制是否生效"要解析 `query-order` 的 `itemName`（或直接比对我们自己的入参）。

## 4. 所有看到的状态文字（按出现顺序）

| 顺序 | 时刻 | 接口 | `orderStatus` | `status` | 场景 |
|---|---|---|---|---|---|
| 1 | 18:58:45 | `create-order` | 待支付 | `10` | 下单成功、未付款 |
| 2 | 18:58:51 | `query-order` | 待支付 | `10` | 立刻复查，一致 |
| 3 | 19:14:24 | `query-order` | **订单已取消** | **`60`** | 超时 15 分钟未付款，系统关闭 |
| 4 | 19:14:38 | `query-order` | **订单已完成** | **`40`** | 历史单（2026-05-24） |
| 5 | 19:14:32 | `order-list` | 订单已取消 / 订单已完成 | （无码） | 3 条历史 |

**⚠️ 与 App 的一致性**：App 显示「待支付」，与 `orderStatus` 完全一致 → **以 `orderStatus` 为准，不要自己造词**。

**⚠️ 与工具文档的冲突**：文档说 `status` 枚举是 `1待支付、2配餐中-已支付、4配送中、6已完成、7已取消、8已评价、10配餐中-餐厅确认配餐中`。
实测：`10`=待支付、`40`=已完成、`60`=已取消。**文档那套码值在本链路完全不成立**，疑似另一条业务线/旧版。写代码时**用文字为主键、码为辅键**。

## 5. 付款时限

| 项目 | 值 |
|---|---|
| 字段 | `expirePayTime`（`create-order` 在 `data.orderDetail.expirePayTime`，`query-order` 在 `data.expirePayTime`） |
| 本次 | 创建 `18:58:45` → 截止 `19:13:45` = **900 秒 / 15 分钟** |
| 历史单 | 创建 `13:13:23` → 截止 `13:28:23` = 同样 15 分钟 ✔ |
| 超时行为 | **系统自动关闭订单**，`orderStatus` 变「订单已取消」、`status=60`，**未扣款** |
| App 文案 | 「13分钟内未支付，订单将会被取消」（App 自己也算了个剩余分钟数） |
| 超时后其他字段 | `pickupCode` 仍 `""`、金额仍 `"33.5"`（**不归零**）、`payId` 仍在、`expirePayTime` 原样保留 |

**对 mcspeak 的要求**
1. 下单后**立刻**把 `orderId` + `payH5Url` + `expirePayTime` 存下来（`query-order` 拿不到支付链接）。
2. 展示倒计时用 `expirePayTime`，**不要用"15 分钟"硬编码**（不同门店/活动可能不同）。
3. 过期后要能识别「订单已取消」并提示"未扣款，可重新下单"，**不要说"已过期"**（那是我们自己的词，App 上没有）。
4. **绝不能靠金额或 pickupCode 判断订单有效性** —— 超时后它们都不变。

## 6. 定制项是否真的进了订单？

**进了，而且是明文回显。** 下单参数与订单回显对照：

| 我们传的 | 订单里的 `itemName` | 结论 |
|---|---|---|
| `1440` + `100136(key=0-1)` + `120512(key=0-0)` | `麦辣鸡腿汉堡 切块生菜(不要)` | ✅ 开关组：`0-0` = 去掉，生效 |
| `3050` + `200002(key=0-0)` | `可乐中杯 冰(去冰)` | ✅ 单选组：`0-0` = 去冰，生效 |
| `4810`（无特调） | `中薯条` | ✅ 没有多余后缀 |

**渲染规律**（从 3 个样本推得，含历史单的 `冰(少冰)`）：
```
{商品名} {特调组名}({选中项名称})
去掉配料 → {物料名}(不要)
```
- 历史单里是 `咕噜咕噜橘子风味冻冻汽水 冰(少冰)` —— **多冰量组统一渲染成 `冰(xx)`**，组名就是"冰"。
- `(不要)` 是"去掉"的专用后缀。

**对本 Skill 的两条硬规则**
1. **卡片文案不要解析 `itemName`**（`冰(少冰)` 这种中文拼接无法可靠反解）。卡片内容用**我们自己的下单参数** + `menu_tags.md` 生成，`itemName` 只用来**校验**：出现 `(不要)`/`(去冰)` 就说明传对了。
2. 如果订单里**没有**出现预期的 `(不要)`，说明特调没生效 → 必须提示访客"请在柜台再口头确认一次"，不能默认成功。

## 7. 还缺哪些状态没测到

| # | 缺失状态 | 为什么重要 | 怎么补 |
|---|---|---|---|
> **2026-10-24 22:30 更新**：下表 1–3 项已在真实付款一单后补齐（App 实测五态：待支付 → 确认中 → 配餐中 → 待取餐 → 订单已准备完毕），最新结论以 `order_status_map.md` 为准。

| 1 | **待取餐 / 备餐完成**（★ 最高优先） | 取餐卡的触发条件；这是唯一"现在去拿"的时刻 | 需真实付款一单（¥20 内单品），付款后轮询 `query-order` |
| 2 | **配餐中 / 制作中** | 付款后第一状态，决定"已付款，正在做"的提示 | 同上，付款后立即查 |
| 3 | **配餐中-餐厅确认** | 门店接单环节，可能出现异常分支 | 同上 |
| 4 | **用户主动取消**（`cancel-order`，reason=1） | 是否也是 `60`？与超时取消是否可区分？ | 需再下一单，然后调 `cancel-order`（本轮因改为自然过期未测） |
| 5 | **已评价** | 评价后的终态 | 需取餐后在 App 评价 |
| 6 | **退款中 / 已退款** | 已付款后取消的退款链路 | 需付款后取消 |
| 7 | **付款成功但订单异常**（付款后门店关单） | 真实客诉场景 | 难构造，靠线上兜底 |
| 8 | **配送中**（外送） | 不在 mcspeak 范围 | 可跳过 |

> 建议下一轮：**下一单最便宜的单品（如 `515837` 圆筒 ¥5 或 `3505` 锡兰红茶 ¥11.5），实际支付**，付款后 5 秒 → 1 分钟 → 3 分钟各查一次，就能补齐 1/2/3 三个最关键的中间态，并拿到**真实的 `pickupCode`**。
